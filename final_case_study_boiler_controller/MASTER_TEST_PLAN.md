# Master Test Plan — Smart Boiler Safety Controller

## 1. Document Purpose
Цей план описує, як перевірено контролер **електричного котла для опалення** **Smart Boiler Safety Controller (SBSC)** і на яких доказах будується рішення про реліз.
Рішення, яке має підтримати тестування: **чи можна випускати поточний BUGGY build у пілотну експлуатацію**.
Головне питання якості: чи залишається ТЕН у безпечному стані за будь-якого збою — шуму на вході, відмови датчика, зависання прошивки, аварійного reset, втрати мережі та тривалої роботи.

## 2. System Overview

| Підсистема | Компоненти | Функція в котлі |
|---|---|---|
| MCU | ESP32 DevKit V1 | Логіка термостата, керування, діагностика |
| Датчик приміщення | DHT22 (GPIO15) | Температура / вологість для термостата |
| Датчик теплоносія | I2C-сенсор (стенд: MPU6050, 0x68, SDA 21 / SCL 22) | Температура контуру, захист від перегріву |
| Нагрів | Реле ТЕН (GPIO5) | Головний виконавчий елемент, критичний для безпеки |
| Модуляція | PWM 0–100 % (GPIO2) | Ступені потужності ТЕН / швидкість циркуляційного насоса |
| Змішувальний клапан | Привод з двома реле і двома кінцевиками | Відкрити / закрити клапан контуру опалення, ніколи обидва напрямки одночасно |
| Локальне керування | Кнопка BOOST / ручного режиму, LED статусу | Ручне ввімкнення нагріву, індикація |
| Сервісний порт | UART CLI 115200 | Налаштування, діагностика, автотести |
| Пам'ять | NVS (Preferences) | Налаштування, стан реле, лічильники |
| Надійність | Task Watchdog, deep sleep, reset reason | Відновлення після зависання, енергозбереження |
| Мережа | Wi-Fi / MQTT, офлайн-буфер на 8 повідомлень | Телеметрія в хмару, віддалений моніторинг |

**Критичні дані та виходи:** стан реле ТЕН, показання температури, налаштування в NVS, телеметрія з унікальними message ID.

**Зовнішні залежності:** MQTT-брокер, Wi-Fi, живлення, фізичні датчики.

## 3. Quality Objectives
1. **Safety:** після будь-якого збою, reset або команди RESET нагрів вимкнений (fail-safe).
2. **Коректність вимірювань:** невалідні дані датчика ніколи не трактуються як реальна температура.
3. **Надійність:** зависання завершується контрольованим відновленням; немає boot loop.
4. **Цілісність даних:** збережений стан — або старий, або новий валідний; телеметрія без втрат і дублікатів.
5. **Стабільність:** немає систематичної деградації пам'яті і reconnect storm.
6. **Діагностованість:** STATUS / логи правдиво відображають стан.

## 4. Scope
- Цифрові входи: кнопка, дребезг і шум.
- UART CLI: позитивні, граничні та негативні сценарії, автоматизація pytest.
- I2C-датчик: аналіз протоколу (Logic Analyzer + PulseView), поведінка при NACK.
- Виконавчі елементи: реле ТЕН, PWM, привод клапана з кінцевиками.
- Recovery: watchdog, deep sleep / wake, power loss, перерване збереження NVS.
- Мережа: NET DOWN / UP, retry/backoff, офлайн-буфер, межа буфера, дублікати, 20× reconnect.
- Довготривала стабільність: stress і тренд heap.

## 5. Out of Scope
| Що не тестується | Чому |
|---|---|
| Електрична безпека силової частини (ізоляція, контактори ТЕН, УЗО), сертифікація | Потрібне фізичне обладнання і лабораторія |
| Гаряче водопостачання (ГВП) | Продукт — котел лише для опалення: немає контуру ГВП, датчика протоку і клапана пріоритету |
| Газове обладнання (полум'я, газовий клапан, розпал, тяга) | Котел електричний |
| Реальний brown-out і поведінка Flash при фізичній втраті живлення | Wokwi моделює powerloss командою, не напругою |
| Реальний Wi-Fi / TCP / MQTT QoS | NET DOWN / UP — модель недоступності брокера |
| Енергоспоживання, температурний режим плати | Немає вимірювального стенду |
| Інтеграційна збірка всіх підсистем в одній прошивці | Підсистеми перевірялись на окремих стендах (див. 6) |
| Аналіз вихідного коду | Тестування black-box |

## 6. Assumptions / Constraints
- Продукт перевірявся **по підсистемах на окремих Wokwi-стендах**, кожен зі своєю BUGGY-збіркою прошивки (курсові стенди тижнів 1–7). Інтеграційний системний тест повної збірки — residual risk.
- Стенд приводу клапана (тиждень 1) працював на Arduino Uno; решта — ESP32 DevKit V1.
- I2C-датчик теплоносія на стенді представлений MPU6050 (регістр температури) — перевіряється протокол і обробка помилок, а не конкретний сенсор.
- Час у логах — час симуляції Wokwi або годинник ПК; швидкість симуляції не дорівнює реальному часу.
- Логічний аналізатор — Wokwi Logic Analyzer (VCD), декодування в PulseView.

## 7. Quality Risks

| Risk ID | Risk | Impact | Probability | Priority | Mitigation / Test |
|---|---|---|---|---|---|
| R01 | Шум або дребезг на кнопці BOOST створює хибну дію — нагрів вмикається без команди | High | High | **P1** | Scripted noise / bounce (scenario.yaml), Logic Analyzer, лічильник натисків |
| R02 | Сервісний CLI приймає некоректні параметри або перезавантажується від вводу | Medium | High | **P2** | Boundary / negative CLI, pytest-набір |
| R03 | Відмова датчика не детектується: 0.0 °C або зависання на I2C трактуються як норма | High | Medium | **P1** | Відключення DHT22, I2C fault injection + PulseView |
| R04 | Прошивка зависає без відновлення | High | Medium | **P1** | WDT fault injection (hang), I2C NACK, 10× recovery |
| R05 | Після reset / RESET / power loss ТЕН залишається ввімкненим | Critical | High | **P1** | relay on → hang / powerloss / RESET → STATUS |
| R06 | Перерване збереження пошкоджує налаштування без виявлення | High | Medium | **P1** | powerloss під час save, before / after |
| R07 | Привод клапана: обидва напрямки одночасно або рух без таймауту | High | Medium | **P1** | State-machine тести, кінцевики, таймаут 10 s |
| R08 | Reconnect storm при недоступному брокері | Medium | High | **P2** | NET DOWN, інтервали retry за мітками часу, 20× reconnect |
| R09 | Втрата або дублювання телеметрії при офлайн-буферизації | High | High | **P1** | Message ID до / після flush, межі 8 / 9 / 12 |
| R10 | Витік пам'яті при тривалій роботі | Critical | High | **P1** | STRESS 100 ×10, Memory Stability Log |
| R11 | Неточні таймери (sleep, WDT) | Medium | Medium | **P2** | sleep 5 / 10 / 20, вимірювання wake і WDT timeout |
| R12 | STATUS / лічильники показують неправду | Medium | High | **P2** | Звірка STATUS з логом і діями |

Impact × Probability → Priority: P1 — блокує реліз до виправлення і регресії; P2 — потрібне виправлення або прийняте обґрунтоване рішення.

## 8. Test Levels
| Рівень | Що перевіряється | Приклад |
|---|---|---|
| Component / firmware function | Окрема функція прошивки | Debounce кнопки, парсер CLI, PWM |
| Interface / protocol | UART, I2C, JSON-відповіді | PulseView-декодування, валідність JSON |
| System | Поведінка контролера цілком на стенді | Цикл привода клапана, термостат + реле |
| Recovery / fault injection | Реакція на зависання, reset, power loss | hang, powerloss, FAULT ON / OFF |
| Network | Втрата зв'язку, буфер, flush | NET DOWN / UP, 20× reconnect |
| Regression | Повторний запуск після змін | pytest-набір, run_scenarios.py, scenario.yaml |

Functional, boundary / negative, protocol, reliability, recovery, persistence, network stress, memory stability, automation.

## 11. Entry Criteria
- Збірка компілюється (PlatformIO Build SUCCESS) і стартує у Wokwi; boot log і CLI доступні на 115200.
- Схема стенда відповідає опису (піни, номінали, підключені датчики).
- Є вимоги до підсистеми і шаблони протоколу / bug report.
- Для автотестів: venv з requirements.txt, DEVICE_PORT доступний, Serial Monitor закритий.

## 12. Exit Criteria
| Критерій | Ціль |
|---|---|
| P1-ризики покриті тестами | 100 % |
| Критичні тести (safety, recovery, persistence) | 100 % PASS |
| Відкриті Critical-дефекти | 0 |
| Відкриті Major-дефекти | 0 або прийняті з обґрунтуванням |
| Відтворюваність кожного дефекту | ≥ 2 прогони, для Critical ≥ 3 |
| Evidence | для кожного FAIL — лог / трейс / вивід pytest, достатній для перевірки іншою людиною |
| Регресія | повний автоматизований набір PASS на фінальній збірці |

## 13. Regression Strategy
| Тригер | Що запускається |
|---|---|
| Будь-яка зміна прошивки (smoke, ≈10 хв) | pytest: status, ping, LED, RESET, межі PWM; run_scenarios.py A і B; boot + reset reason |
| Зміна input / debounce | scenario.yaml (норма, шум 5 ms, heavy bounce) ×5, Logic Analyzer |
| Зміна CLI / парсера | повний pytest-набір (67 тестів) + boundary / negative з тижня 3 |
| Зміна драйвера датчиків / I2C | FAULT ON / OFF + PulseView, відключення DHT22 |
| Зміна recovery / NVS / power | hang ×10, relay on → hang / powerloss → STATUS, перерване save ×5 |
| Зміна network stack | run_scenarios.py повністю (A–F, 20× reconnect), Memory Stability Log |
| Release candidate | усе вище + 3 повні прогони для відтворюваності |

## 14. Evidence Strategy
| Тип знахідки | Обов'язковий evidence |
|---|---|
| Логіка / стан | Serial log з мітками часу: команда → відповідь → STATUS після |
| Вхідні сигнали, протокол | VCD + скриншот PulseView з маркерами (last ACK, first NACK) |
| Recovery | Boot log: reset reason, час до відновлення, стан виходів після |
| Persistence | STATUS before / after, кількість повторів |
| Мережа / дані | Список message ID і кількість publish на кожен ID, лічильники |
| Пам'ять | Memory Stability Log: heap на кожній ітерації, Δ на повідомлення |
| Автоматизація | Вивід pytest (-v), сирий UART-лог прогону |
| Будь-який FAIL | Класифікація: Test / Environment / Communication / Requirement / Firmware |

## 15. Defect Management
- **Severity:** Critical — безпека, втрата даних, деградація до відмови; Major — порушена важлива вимога без обхідного шляху; Medium — часткова відмова або є обхід; Minor — косметика, неточний лог.
- **Reproducibility:** x/N прогонів; Critical підтверджується ≥ 3 прогонами.
- **Обов'язкові поля:** title, requirement / risk, environment, preconditions, steps, expected, actual, evidence, severity, reproducibility, suggested fix.
- **Retest:** кожен виправлений дефект — повтор його кроків + регресійний пакет відповідної підсистеми.

## 16. Residual Risks
- Інтеграція: підсистеми ніколи не працювали в одній збірці; взаємний вплив (наприклад, I2C hang + MQTT flush + WDT) не перевірено.
- Реальне залізо: brown-out, Flash / NVS при фізичній втраті живлення, реальний дребезг кнопки, наводки на лінії датчиків.
- Реальна мережа: Wi-Fi ≠ broker; QoS / PUBACK, кілька нод на одному брокері.
- Довготривалі прогони (доби) — витік 80 B на повідомлення дасть відмову через години.
- Таймінги: швидкість симуляції ≠ реальний час (WDT, sleep, backoff).
