# Webinar 3 — UART CLI: robustness testing

ESP32 з текстовим CLI по UART 115200 (Wokwi): `help`, `status`, `set speed <0..255>`, `set timeout <1..60>`, `led on/off`, `save`, `reset`. Вимоги REQ-01…REQ-16: межі значень, регістр команд, невалідний ввід, максимальна довжина рядка 40 символів, однакова реакція на помилки незалежно від стану, жодних перезавантажень від вводу.
Тестування black-box: boundary value analysis, negative, input length, state / sequence, stress input.

## Результати

36 тестів: PASS — 30, FAIL — 6. Кожен дефект відтворено 5 з 5.

| ID | Дефект | Severity |
|---|---|---|
| BUG-05 | Рядок довший за 40 символів → SYSTEM FAULT і reboot замість `ERROR: command too long` (межа точно 40 / 41) | Critical |
| BUG-02 | Невалідна команда `set` у стані CONFIG=DIRTY → reboot і втрата незбереженої конфігурації; у стані SAVED — звичайна помилка | Critical |
| BUG-01 | `set timeout 0` приймається (діапазон 1…60) | Major |
| BUG-06 | `set speed 256` мовчки обрізається до 255 | Major |
| BUG-04 | `!@#$%^&*()` → `OK` | Minor |
| BUG-03 | `STATUS` виконується як `status` (вимога: регістр важливий) | Minor |

Рішення: **NO-GO** — два способи перезавантажити пристрій звичайним вводом.

## Оновлення після рев'ю
- Bug reports для всіх 6 дефектів (раніше 3).
- Actual — з реального логу; Expected для `status` і `led on` — очікуваний результат; виправлено суперечності в тестах зі speed 256 і довгим рядком.
- Послідовності — окремими кроками 1) … 2) … 3) …
- Точна межа довжини (40 / 41) і пояснення, чому в першій версії reboot спостерігався після рядків по 32 і 33 символи.
- BUG-02: названо причину (стан DIRTY) і додано порівняння зі станом SAVED зі скриншотами.
- Reproducibility — 5/5 замість «Always»; BUG-01 — Major замість Middle; розділ про межі переписано таблицями з поясненням N−1 / N / N+1.
